🔗 Crafted Attack URL

Decoded: serviceurl=https://crm.zoho.com@evil.com/ → Browser resolves to evil.com (crm.zoho.com is userinfo, not hostname)

Step-by-Step Reproduction
STEP 1 Get session cookies — GET the login page with injected serviceurl
Send a GET request to the Zoho signin page with the malicious serviceurl. This sets CSRF cookie (iamcsr) needed for all subsequent requests.
curl · Step 1 · GET session cookies
curl -s -c /tmp/cookies.txt \
  -D /tmp/headers.txt \
  'https://accounts.zoho.com/signin?servicename=ZohoCRM&serviceurl=https%3A%2F%2Fcrm.zoho.com%40evil.com%2F' \
  -H 'User-Agent: Mozilla/5.0 (X11; Linux x86_64) AppleWebKit/537.36' \
  -o /dev/null

# Extract CSRF token from cookie jar
grep iamcsr /tmp/cookies.txt

STEP 5 Zero-validation redirect — switchto() called with injected URL
Zoho's signin JS calls switchto(redirect_uri) on all auth success codes. The function has zero domain validation — it blindly navigates to whatever URL the server returned.
// From signinnew.js — auth success handler (multiple locations)
if("SI302"===successCode || "SI200"===successCode || "SI300"===successCode ||
   "SI301"===successCode || "SI303"===successCode || "SI305"===successCode ||
   "SI507"===successCode || "SI509"===successCode || "SI506"===successCode)
  return switchto(jsonStr[signinathmode].redirect_uri), !1;

// switchto() definition — ZERO domain validation
function switchto(url) {
  // No allowlist check. No origin comparison. No warning.
  window.top.location.href = url;  // ← directly navigates to attacker domain
}
Full Attack Flow
① Attacker sends crafted link to victim
https://accounts.zoho.com/signin?servicename=ZohoCRM&serviceurl=https%3A%2F%2Fcrm.zoho.com%40evil.com%2F
② Victim sees legitimate Zoho login page — no warning
accounts.zoho.com shows "Sign in to access CRM" — victim trusts it
③ Victim completes authentication (OTP / password / SSO)
Server validates credentials, returns SI302 (or SI200/SI300/SI301 for most users)
④ switchto(redirect_uri) — Zoho JS navigates browser to evil.com
redirect_uri contains serviceurl=https://crm.zoho.com@evil.com/ → browser resolves to evil.com
⑤ Victim lands on attacker-controlled evil.com
No redirect warning ever shown · Auth tokens may leak via Referer header · Full phishing page displayed
Why Zoho's Redirect Warning Is Bypassed

Zoho shows an "external site redirect" warning dialog for direct serviceurl=https://evil.com. The @ userinfo trick bypasses this check:

BLOCKED — Warning Shown
serviceurl=https://evil.com/

→ Server sees external domain
→ Warning dialog triggers
BYPASSED — No Warning
serviceurl=https://crm.zoho.com@evil.com/

→ Server sees crm.zoho.com
→ Treated as internal ✓ bypass
